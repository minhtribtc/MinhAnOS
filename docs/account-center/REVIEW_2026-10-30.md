## 2. Design assessment

Backend / security: sound and close to the plan. One users store, two realms kept, every path through one
policy service, last-admin lock, host operator split, contract-first schemas with generated client, no iframe.

Frontend / app integration: **not yet optimal, and not yet a reusable app standard**.

| # | Issue | Evidence | Impact |
|---|---|---|---|
| F1 | Manifest does not match runtime | manifest `entrypoint: /apps/account-center`, real URL `/accounts/`; `navigation[].path` and `settingsIntegration` are not read by any host | Manifest cannot be used to install/launch apps |
| F2 | App integration is hard-wired in many places | Go `registry` in internal/platform/server.go, `v-else-if` chain in AppContent.vue, icons.ts map, per-app `COPY` in both Dockerfiles, per-app `MountAccounts` | Each new app edits Desktop + both backends; no install/uninstall possible |
| F3 | Lifecycle is ad-hoc props/events | `embedded`, `active`, `session-ended`, `profile-changed`, `canClose` via component ref; app-sdk has no lifecycle API although manifest declares `lifecycle.supports` | Every app invents its own contract with the Shell |
| F4 | Static frontend served from a domain package | `identity.MountAccounts` serves files | UI hosting coupled to Identity; should be a generic platform mount |
| F5 | Monolithic UI component | 7 screens in one AccountsApp.vue, lines up to ~1,800 chars, one state test | Hard to review, test and extend |
| F6 | Mixed app IDs in registry | `files` (legacy) vs `com.minhanos.account-center` | Ambiguous identity for grants/install state |
| F7 | Duplicate admin UI | Settings → Users still active | Two UIs for the same policy |

## 3. App standard: central Settings integration (user rule, 2026-10-30)

User clarified: every app must integrate uniformly with the central Settings app (com.minhanos.settings), like
Settings on iOS/macOS/Android. The binding rule is in AGENTS.md ("Central Settings standard"). Summary:

1. Settings is the single place for system and per-app preferences; apps link into it instead of own settings pages.
2. Apps declare panels in manifest `settingsIntegration`; Settings navigation is built from manifests, not hardcoded.
3. App packages export panel components rendered natively by Settings via app-sdk (no iframe), also usable standalone.
4. Settings data: versioned per-app schema, user/system scope, backend validation + permission, audit for system scope.
5. Uniform UI from @minhanos/ui, `<app>.settings.*` i18n keys, deep links and Settings search.

Still applies from the earlier review: manifest-driven app registry, generic `/apps/<appId>/` mount and an SDK
lifecycle bridge (F1–F4, F6) — the Settings standard depends on the same manifest registry.

## 4. Recommended next steps

1. Platform: manifest-driven registry + SDK lifecycle bridge + Settings shell that renders panels from manifests
   + per-app settings schema/API. Move current hardcoded Settings tabs into panels (Appearance = Desktop,
   My account/Users = Account Center), removing the duplicate admin UI (F7).
2. Make Account Center, then Files, conform (panels, deep links); split AccountsApp per screen; one browser
   acceptance pass to close Phase 4.
3. Phase 5: Files authorization and app access policy editing (as an Account Center/Settings panel).
4. Phases 6–8 as planned.
